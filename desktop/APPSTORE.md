# Putting Plain Sight on the Mac App Store

The Mac App Store is the goal for the desktop app (ledger D-37). This page lists the steps from here to a published app. Everything the app itself needs for the sandbox is in the repository, and so are the export compliance answer and the copyright line (`src-tauri/Info.plist`) and the minimum macOS of 12.0. Still to write, though it needs no account: the privacy policy text inside the app (decision 3). The App Store configuration files (step 6) come from one command, `npm run appstore:config`, once the membership gives the team id, the signing identity and the profile. The rest needs Pranav's Apple Developer Program membership.

## What is already in place

- **App Sandbox.** The app is signed with exactly three entitlements (`src-tauri/Entitlements.plist`): the sandbox itself, read and write access to files the user picks in a panel, and app-scoped bookmarks. There is no network entitlement and none for the Downloads folder: Save without a folder goes through the system save panel (ledger D-49), so the file the user chooses is covered by the user-selected entitlement. The Mac App Store accepts only sandboxed apps (App Review Guidelines 2.4.5(i)).
- **Unsaved text.** Closing the window, quitting, a quit from the Dock and a logout first ask "Quit without saving?" in a standard sheet when the text has changed since the last Save or Open and no vault keeps it, with Cancel as the default button (ledger D-48); Esc stays the deliberate erase.
- **The remembered folder** is kept as a security-scoped bookmark (`src-tauri/src/bookmark.rs`, `src-tauri/src/folder.rs`), which is how a sandboxed app gets back into a folder after a quit.
- **The migration into the container.** `src-tauri/container-migration.plist` tells macOS to bring the vault and the app's data folder into the app's container on the first sandboxed launch (Apple's article says it copies them; in a probe build on 26 October 2026, on macOS 26, macOS moved the data, and folders under the probe's identifier stayed outside the container, `~/Library/WebKit/<id>` (empty) and `~/Library/Caches/<id>` (sbprobe2-run-1, `leftovers`), so keep a copy of the data before the move, ledger D-54).
- **The category** is Productivity (`LSApplicationCategoryType` is `public.app-category.productivity`).
- **The app's own Info.plist keys.** `src-tauri/Info.plist` holds `ITSAppUsesNonExemptEncryption` set to false (the app encrypts only through the system's WebCrypto; Pranav approved the answer on 21 October 2026, ledger D-46) and `NSHumanReadableCopyright` ("Copyright 2026 Pranav Ongole. MIT License."). The Tauri CLI finds the file by its place next to `tauri.conf.json` (tauri-cli 2.12.3, `src/interface/rust.rs`, the `Info.plist` lookup) and the bundler merges it into the app's Info.plist (tauri-bundler 2.10.3, `src/bundle/macos/app.rs`, `create_info_plist`: each key of the file is inserted over the template's). The config check requires exactly those two keys and the bundle check reads them back from the built app.
- **`LSRequiresCarbon` stays.** The bundler's template inserts `LSRequiresCarbon` true unconditionally (tauri-bundler 2.10.3, `src/bundle/macos/app.rs` line 334) and the merge of `src-tauri/Info.plist` can only add or replace keys, never remove one (the same file, lines 352 to 361: `plist.insert(key, value)` for each key of the file). So the key cannot be dropped through `Info.plist`; it could only be set to another value, which would leave a deprecated key in place with a stranger value. It stays true, as it does in every app built with this bundler version that does not override the key; Carbon.framework stays linked by tao for keyboard layouts.
- **The minimum macOS** is 12.0 (`bundle.macOS.minimumSystemVersion`), Tauri's rule for a build that is Apple Silicon only (Tauri, App Store guide, section Build: "If you prefer to only support Apple Silicon instead, you must change tauri.conf.json > bundle > macOS > minimumSystemVersion to 12.0"); approved by Pranav on 21 October 2026 (ledger D-47). The app was tested on macOS 26 only, and the README says so.

Seen on 26 October in probe builds (sbprobe-run-1, sbprobe2-run-1): the page gave no answer in 31 seconds without a network entitlement and answered with it; the vault and the bookmark file arrive in the container. Not yet seen: the folder panel and the save panel inside the sandbox. The build as it stands, with the three entitlements above, would open no page in the sandbox; adding the network entitlement is Pranav's decision (decision 2 below). The Product Owner checks the rest in a launched sandboxed build of the final candidate before anything below is done.

## Decisions Pranav makes first

1. **Export compliance.** Decided: `ITSAppUsesNonExemptEncryption` is false in `src-tauri/Info.plist` (Pranav, 21 October 2026, ledger D-46). The app encrypts the user's own text on the Mac with the system's WebCrypto (AES-256-GCM, PBKDF2) and sends nothing. Apple says encryption built into the operating system is typically exempt from the documentation upload, while proprietary encryption is not, and that the developer is responsible for the answer ([Complying with Encryption Export Regulations](https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations), [Overview of export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance)). Apple's "Overview of export compliance" page also notes that France controls "Secure Storage" apps separately, which may matter for the vault; whether a yearly US self-classification report applies is Pranav's own filing.
2. **A network entitlement**: the probe of 26 October shows the page needs it; Pranav decides.
3. **A privacy policy.** Apple requires a link to it in App Store Connect and inside the app, in an easily accessible place (Guideline 5.1.1(i)). The app cannot open links, so the policy text itself would go into the app, for example in the intro.
4. **Which Macs.** Decided: Apple Silicon only, minimum macOS 12.0 (Pranav, 21 October 2026, ledger D-47). Tauri's App Store guide says such a build must declare macOS 12.0 as its minimum, or be built as a universal app for Intel Macs too ([Tauri, App Store](https://v2.tauri.app/distribute/app-store/), section Build).

## Steps

1. **Join the Apple Developer Program** at developer.apple.com (SIGNING.md, step 1). Note the team id: it is shown under Membership details.
2. **Register the App ID.** In Certificates, Identifiers and Profiles, choose Identifiers, click +, choose App IDs, then App. Enter the description "Plain Sight" and the explicit Bundle ID `com.pranavongole.plainsight`, which must match `identifier` in `src-tauri/tauri.conf.json`. No extra capabilities are needed.
3. **Create the two certificates.** In Xcode, open Settings, Accounts, select the Apple account, click Manage Certificates, click + and add "Apple Distribution" (it signs the app), then click + again and add "Mac Installer Distribution" (it signs the installer package). Run `security find-identity -v` and note both identity names exactly as listed. The configuration command of step 6 takes only an "Apple Distribution" identity: Apple's [certificates overview](https://developer.apple.com/help/account/certificates/certificates-overview/) still lists the older "Mac App Distribution" type ("Sign a Mac app before submitting it to the Mac App Store"), and the command refuses it, so create the Apple Distribution certificate even if you have the older one.
4. **Create the provisioning profile.** In Certificates, Identifiers and Profiles, choose Profiles, click +, and under Distribution choose "Mac App Store Connect". Select the App ID from step 2 and the Apple Distribution certificate from step 3, name the profile "Plain Sight App Store", then download it. Keep it outside the repository.
5. **Create the app record.** In App Store Connect, open Apps, click +, choose New App, then macOS. Enter the name (at most 30 characters, Guideline 2.3.7), the primary language, the Bundle ID from step 2 and a SKU such as `plainsight-mac`.
6. **Add an App Store configuration** next to the everyday one, so that everyday builds stay ad-hoc signed. With the team id from step 1, the Apple Distribution identity from step 3 and the profile from step 4, run from `desktop/`:

   ```
   npm run appstore:config -- --team <team id> --identity "Apple Distribution: <name> (<team id>)" --profile "<path to the profile from step 4>" --build 1
   ```

   It writes `src-tauri/tauri.appstore.conf.json` (never `tauri.macos.conf.json`, a name Tauri merges into every macOS build):

   ```json
   {
     "bundle": {
       "macOS": {
         "signingIdentity": "Apple Distribution: <name> (<team id>)",
         "minimumSystemVersion": "12.0",
         "entitlements": "./Entitlements.appstore.plist",
         "files": {
           "embedded.provisionprofile": "<path to the profile from step 4>"
         },
         "bundleVersion": "<the build number>"
       }
     }
   }
   ```

   and `src-tauri/Entitlements.appstore.plist`. Tauri copies each `files` entry into the app's `Contents` folder, so the profile lands at `Contents/embedded.provisionprofile`, where macOS looks for it; the command writes the profile's absolute path there. Tauri merges this file over `tauri.conf.json`, so the container migration manifest stays bundled and `minimumSystemVersion` repeats the everyday value. `Entitlements.appstore.plist` holds the three entitlements of `Entitlements.plist`, read from that file each time the command runs, plus the two that tie the app to the profile, five in all: `com.apple.application-identifier` set to `<team id>.com.pranavongole.plainsight`, and `com.apple.developer.team-identifier` set to `<team id>` (Tauri's App Store guide, Entitlements). The command requires the build number and writes it as `bundle.macOS.bundleVersion`; without that key, Tauri "derives the CFBundleVersion from the value defined in tauri.conf.json > version" (Tauri's App Store guide, Build and upload), 1.0.0 here. App Store Connect identifies each upload by its build number (Upload builds, step 11), and Apple's [CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion) page says "missing integers in the format are interpreted as zeros. For example, 0 specifies 0.0.0, 10 specifies 10.0.0" and "For macOS apps, increment the build version before you distribute a build", so 1 and 1.0.0 are the same build. Give `--build 1` for the first store build and a higher number for every later upload (step 8). The command checks everything first and writes nothing when the team id is not ten upper-case letters or digits, the identity does not read "Apple Distribution: <name> (<team id>)", the profile is missing, is not a file, does not end in `.provisionprofile` or lies inside the repository, the build number is missing or is not a whole number from 1, or either file exists already (`--force` replaces them). If macOS will not let it put the second file in place (an earlier file it may not replace, say), it puts the first back as it was and says so; if even that fails, it says where the earlier configuration waits, and the two files are from two runs until it is moved back (with no earlier configuration, it names the new one, to be removed by hand). The two files hold this Mac's path to the profile and the team's identifiers, so they are not committed: `desktop/.gitignore` lists them. The everyday build is unchanged: `tauri.conf.json` and `Entitlements.plist` stay as they are, `tests/config.mjs` and `tests/bundle.mjs` check that build, and the command has its own tests (`tests/appstore-config-tests.mjs`); step 9 checks the signed store build.
7. **The export compliance answer** is in place: `src-tauri/Info.plist` holds `ITSAppUsesNonExemptEncryption` false and the copyright line, and every build merges it in (see "What is already in place"). Nothing to do here.
8. **Build the app.** Every upload needs a higher build number than the one before (step 6): the configuration from step 6 carries `--build 1` for the first store build, and before each later one, run step 6's command again with the next number and `--force` (`--build 2`, then 3, and so on), since Apple counts 1 and 1.0.0 as the same build. Then, from `desktop/`, run `npx tauri build --bundles app --config src-tauri/tauri.appstore.conf.json`. Leave `APPLE_ID`, `APPLE_PASSWORD` and the API key variables unset: those make Tauri notarize, which is for Developer ID copies and not for the App Store. For a universal build add `--target universal-apple-darwin` after `rustup target add x86_64-apple-darwin`; the app is then in `src-tauri/target/universal-apple-darwin/release/bundle/macos/`.
9. **Check the signed app** before packaging: `codesign -dv --verbose=4 "<app>"` names the Apple Distribution certificate and the team id; `codesign -d --entitlements - --xml "<app>"` shows exactly the five entitlements; `Contents/embedded.provisionprofile` exists; `codesign --verify --deep --strict "<app>"` reports nothing.
10. **Make the signed installer package.** Tauri 2.12 has no installer package format of its own (its macOS formats are `app` and `dmg`), so use Apple's `productbuild`, as Tauri's guide does: `xcrun productbuild --sign "<Mac Installer Distribution identity from step 3>" --component "<app>" /Applications "Plain Sight.pkg"`.
11. **Upload the package.** Apple lists Xcode, Transporter, `altool` and the App Store Connect API as the ways to upload a build ([Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)). The simplest is Transporter from the Mac App Store: sign in, drag `Plain Sight.pkg` in, click Deliver. From Terminal: create an App Store Connect API key. Apple's "Creating API Keys for App Store Connect API" page makes a Team Key under Users and Access, Integrations, Team Keys, with the access Developer; Tauri's App Store guide says Integrations, Individual Keys. Follow whichever your screen shows, and check `xcrun altool --help` for `--api-key-subject` if an upload with an individual key is refused. Save the key file as `~/.appstoreconnect/private_keys/AuthKey_<key id>.p8`, then run `xcrun altool --upload-app --type macos --file "Plain Sight.pkg" --apiKey <key id> --apiIssuer <issuer id>`. `notarytool` is not used: it notarizes Developer ID copies.
12. **Test the store build with TestFlight** once App Store Connect has processed it (an email says so). Install it from TestFlight on this Mac and use it for a day.
13. **Fill in the listing** in App Store Connect:
    - Category: Productivity, matching the app.
    - Privacy policy URL, and the same policy inside the app (decision 3).
    - App Privacy: choose "Data Not Collected". Apple defines collecting as transmitting data off the device ([App privacy details](https://developer.apple.com/app-store/app-privacy-details/)); the app sends nothing.
    - Export compliance: the answer from decision 1.
    - Age rating: answer the questionnaire honestly (Guideline 2.3.6). The app has no objectionable content, no web access and no user-generated content shared with others.
    - Screenshots: at least one, 16:10, at 1280 x 800, 1440 x 900, 2560 x 1600 or 2880 x 1800 pixels ([Screenshot specifications](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications)), plus the description, keywords and support URL.
    - Price: set only in App Store Connect under Pricing and Availability. Nothing in the app or the repository holds a price, so a price change is a form there, with no build and no review, and it can be scheduled ahead. Decided (ledger D-53): 19.99 US dollars one-time, with a 14.99 launch price for the first weeks; no subscription and no in-app purchase in V1.
14. **Submit for review** with the notes below, then release.

## On this Mac, after the switch

macOS ties the app's container to the app's signature. A build with a different signature, such as the store build after ad-hoc builds, makes macOS ask "would like to access data from other apps" on its first launch; if that is refused at launch, the app does not start ([Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)). Each new ad-hoc build gets a new signature, so it can ask again. Allow it once for the store build; the store builds that follow share one signature and do not ask.

The folder choice is dropped at the switch. The app before the sandbox kept the chosen folder as a plain path in `folder.txt`, and inside the sandbox a path opens nothing: the app may only enter a folder the user picked in the panel, or one a security-scoped bookmark lets it back into. So every build of this branch removes `folder.txt` at launch, sandboxed or not (`Folder::with` in `src-tauri/src/folder.rs`), and the page asks for the folder again; the vault and the rest of the app's data are brought into the container as described above (moved, in the probe build of 26 October; copied, by Apple's article). Choose the folder once more under the ? button after the switch (the README's folder bullet says the same). One consequence before the switch: an unsandboxed launch of this branch (`npm run app:dev`, or the test build's binary outside the harness) uses the real identifier's data folder and removes `folder.txt` at start, so one such launch on Pranav's Mac before his move makes his present app forget its folder; the test harness moves the app's data aside first, a dev launch does not.

## What App Review may ask, and what to write in the review notes

The app's purpose is to show a plausible document while the real text stays hidden. The review notes should say so plainly, because:

1. **Nothing may be hidden from the reviewer** (Guideline 2.5.19: no hidden, dormant or undocumented features). List every key chord and what it does, how to see the real text, how the vault opens and what Esc does, in the notes and in the app's own intro.
2. **New features need a specific description** in the Notes for Review (Guideline 2.3.1(a)). Give a short walkthrough: type, peek at the real text, save into a folder, quit, reopen the vault.
3. **It must be more than a repackaged website** (Guideline 4.2). Name what the app adds: Save into a chosen folder on every Mac, as `.txt`, `.md` or `.docx` (the web page can do this only in Chromium browsers), a vault kept in the app's own data, quitting and closing that wipe the screen first, and a menu bar of its own.
4. **It must work on launch** (Guideline 2.1(a)). An app that opens a blank window is rejected as incomplete; the sandboxed probe of 26 October gave no answer from its page in 31 seconds without the network entitlement, so this item is settled only when the final build has been launched sandboxed.
5. **Explain each entitlement in the review notes**: the folder panel, the Open panel and the save panel (files the user picks), and the remembered folder (app-scoped bookmarks). Guideline 2.4.5(i) itself asks that the app be appropriately sandboxed.
6. **Unsaved text is not lost in silence.** Say in the notes that closing or quitting with text on the page that has changed since the last Save or Open, and no vault open, shows a standard "Quit without saving?" sheet (Cancel is the default button; Quit erases), that a logout is stopped by Cancel as in any document app, and that Esc is the deliberate erase the intro explains (Guideline 2.1(a) rejects apps that "crash or exhibit obvious technical problems"; a silent erase on quit is what a reviewer may read as one; APP_STORE_ISSUE_7).
7. **Data handling** (Guideline 5.1.1): no account, no server, no analytics, nothing sent; the vault is encrypted on the Mac with the phrase only the user knows.
8. **The reviewer may ask why text is hidden at all.** The answer to give: privacy from people who can see the screen, such as in an office, on a train or while sharing a screen. The text never leaves the Mac and the user can always see it.
9. **The positioning sentence to use everywhere**, in the notes, the description and the privacy text: "We store no data. Everything you write stays on your device, where we cannot reach it." The proof behind it: no account, no server, no analytics; the vault is encrypted on the device under a phrase only the user knows; the app runs in the App Sandbox. Never use "spies", monitoring evasion, "unbreakable", "military grade", or "secure" without saying secure from what (BR-22; the review sheet's issue 14).
