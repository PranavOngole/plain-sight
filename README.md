# Plain Sight

Write in private where everyone can see your screen.

Type anything and the screen shows a believable document being written: a novel, a work document or a research paper. Your real words go into a hidden buffer that never touches the network. A chord shows them to you, a key erases them, and when you save a `.sight` file or keep a copy on this device, what is written is ciphertext; a folder save or a plain `.txt` download is plain text, and the page says so where you choose it.

## The promise, and how it is kept

Most privacy claims ask for trust. These ask for a terminal.

| Claim | How it is kept | Check it yourself |
|---|---|---|
| Nothing you type leaves the page. Not a byte. | After it loads, the page requests nothing but its own cover modules from the same origin, and those carry nothing you type: no fetch, no XHR, no beacon, no WebSocket, no form submission, no analytics, no account. The browser enforces it: the page's Content Security Policy is `default-src 'none'`, so a bug could not send a request; the one thing no policy refuses is the page navigating away, and no line of this page does that. | `grep -c -E "fetch\(\|XMLHttpRequest\|sendBeacon\|WebSocket" index.html` prints `0`. Open the browser's network panel and type for a minute: no requests. |
| Nobody else is in the room. | No server-side code, no cookies, no third-party script, no font or image from anywhere else. The deployment is exactly four files, this page and the three covers, by allowlist. | `curl -sI https://cover-story-taupe.vercel.app/` shows no `set-cookie`; `cat .vercelignore` is the allowlist. |
| Your text is one variable in memory. | It lives in a closure. It is written into the page only while you peek and removed when the peek ends. Nothing on `window` returns it. | `grep -n "let real" index.html`; `npm test` includes a check that local storage never holds it. |
| Saving a `.sight` file means encrypting. | AES-256-GCM with a key from your password by PBKDF2-SHA-256 at 310,000 rounds and a random 16-byte salt, a random 12-byte IV, all through the browser's WebCrypto with a non-extractable key. The file is a short JSON record you can read. | Save, open the `.sight` file in a text editor, and compare it with the format below. |
| The device vault stores ciphertext only. | The optional copy in your browser's storage is the same record under a phrase of 12 characters or more; the key exists only in memory while the vault is open. | `npm test` runs the vault round trips with right and wrong phrases. |
| A hostile network sees the page load and nothing of yours. | One load over TLS behind HSTS, then at most the page's own cover files from the same host: there is no keystroke timing to watch because nothing you type is sent. The observer learns the hostname and the size of the loads, never a word. | `curl -sI https://cover-story-taupe.vercel.app/ \| grep -i strict`. |
| You can read every line. | One HTML file and three cover files, no framework, no build step, no runtime dependency, MIT. | `wc -l index.html covers/*.js`. |

What it does not do is listed just as plainly in the threat model below: it cannot stop a keylogger, a compromised machine, a browser extension or someone reading your fingers.

## Who it is for

People who write where someone can see the screen: a newsroom, an open office, a train, a shared flat, a classroom. A journalist drafting a note that is not ready to be seen, a person keeping a journal they do not want to explain, anyone who wants a scratchpad that is nobody's business. The watcher sees a document being written, the page's own short notices and, only if you press the peek chord, your text; never your words otherwise.

## Controls

Ctrl is Cmd on a Mac. Either key works on every platform.

| Action | How |
|---|---|
| Write | Type. Each printable key, Enter and Tab is recorded in the hidden buffer and reveals one more character of the cover. Backspace removes one from both. The buffer is append-only: you cannot move the cursor back and edit earlier text. |
| Peek | Press Ctrl+Shift+G. The cover disappears and your real text is shown. Press it again, type anything, switch windows, or open any dialog, and it is hidden again. |
| Copy | While peeking, press Ctrl+C. Your real text goes to the clipboard. |
| Clear | Press Esc. The hidden buffer and the screen are erased. If the device vault is open it is saved first and then locked; its encrypted copy stays. The page also clears itself if its tab has been hidden for more than 10 minutes while the buffer holds text, a dialog waits for a password, or a phrase is typed on the intro; a typed phrase or password goes with it. |
| Save | The Save button asks for a password and downloads a `.sight` file. If you have chosen a folder on the intro screen, it writes a plain file into that folder instead, as `.txt`, `.md` or `.docx` (Word), whichever you picked there. If you picked a plain download on the intro screen (`.txt`, `.md` or `.docx`), it downloads that file named by the moment, with no password. |
| Open | The Open button reads a `.sight` file, asks for its password and replaces the hidden buffer with its contents. It also reads a plain `.txt` or `.md` note, asking first if there is text on the page. Either way the screen is rebuilt to the same length and writing goes on from there. Esc pressed while a note is still being read cancels it. On an address without encryption a plain note still opens; only a `.sight` file needs it. A `.docx` cannot be opened. |
| Keep on this device | On the intro screen, tick "Keep my text on this device" and choose a phrase of 12 characters or more. From then on the page keeps an encrypted copy of your text in this browser. See the device vault below. |
| Unlock | On a later visit, type your phrase on the blank page, then hold Ctrl, press E, then Enter. The right phrase brings your text back. A wrong phrase does nothing at all. |
| Save to a folder | On the intro screen, "Choose a folder on this computer" (Chrome, Edge and other Chromium browsers; Brave after turning a setting on). From then on Save writes a plain file named by the moment you press it, for example `2026-10-20 14-55-03.txt`, into that folder: `.txt`, `.md` or a Word `.docx`, as picked under "Files in the folder are". "Stop using the folder" brings the download back. |
| Help | The `?` button at the bottom right brings the intro screen back, with the version picker, the vault settings, the save folder and the custom cover text box. |

Other keys pressed with Ctrl, Cmd or Alt held are left to the browser and not recorded. Ctrl+E and Ctrl+Enter are taken by the page only while a vault exists on the device. Shift+Tab is left to the browser too, so keyboard users can reach the buttons (Safari skips buttons by default, so there it is Option+Shift+Tab). Keyboard events with `isComposing` set (input method editors) are ignored. Reloading or closing the tab erases the hidden buffer unless the vault holds a copy; if the buffer is not empty, the browser shows its standard "leave page" prompt first.

## How it works

Everything is in `index.html` (the engine, the styles and the intro) plus one ES module per cover in `covers/`. There is no framework, no build step and no runtime dependency. The only development dependency is jsdom, for the tests.

- A `keydown` listener on `document` handles every key. Printable keys are `preventDefault`ed, appended to a string that lives in a closure, and advance a cursor one character through the cover text.
- The cover is rendered one character per keystroke into paragraphs. A cover line that starts with `## ` becomes a heading, a line that starts with `- ` becomes a bullet in a list, and a line that starts with `[n] ` is typed as text but styled as a reference entry. The markers themselves cost no keystrokes.
- About 3.5 percent of the time, at the start of a word, the cover shows a wrong neighbouring key instead of the right letter; the next keystroke removes it. It costs two keystrokes, one for the wrong letter and one to remove it, and looks like a person correcting a typo. The keystroke right after a correction never produces another one.
- When the cover text runs out, the page inserts a paragraph break and starts the text again from the top.
- The hidden buffer is written into the page only while peeking and is removed again when peeking ends. The page's small console object (`window.PlainSight`) exists for the cover loader and the tests; it returns the cover id and text and nothing that touches the hidden buffer, encrypted or not. Any script that runs inside the page could still capture keystrokes directly, which is the extension and malware caveat below.
- Covers are loaded with a dynamic `import('./covers/<id>.js')` from a small module script, so the page must be served over http. Opened directly from a file, the browser blocks the import and the page shows a notice saying so.
- `localStorage` holds whether you have seen the intro, which cover you picked, any custom cover text you pasted, your download choice (encrypted or plain), a timestamp that tells other open tabs the save folder changed and, only if you turned the vault on, the encrypted copy of your text. It never holds the hidden buffer in clear.

### The device vault

Off by default. On the intro screen, tick "Keep my text on this device" and enter a phrase of at least 12 characters. The page derives a key from the phrase (PBKDF2, SHA-256, 310,000 iterations, a fresh random 16-byte salt) and keeps that key in memory only. It then saves the hidden text to `localStorage` as AES-256-GCM ciphertext with a fresh 12-byte IV: 1.5 seconds after the last keystroke, when the tab is hidden, and when you press Esc. The stored record has the same shape as a saved file (below). Neither the phrase nor the text is stored in clear. If the device refuses the write (storage full, site data blocked, or a note above roughly 3.7 MB in WebKit), the vault locks, a toast says so, and the earlier copy stays; your text stays on the page, and entering the phrase on the intro screen then reopens the vault around the page text as it is, which becomes the copy once the device accepts it. If the copy disappears from the device while the vault is open (site data cleared), the vault locks and says so.

Esc, the 10-minute hidden-tab wipe and closing the tab lock the vault: the key is forgotten and the encrypted copy stays. To come back to your text, type the phrase on the blank page (it shows as cover text like any typing), then hold Ctrl, press E, then Enter. The page derives the key from what you typed and tries to decrypt the copy. If it works, the saved text replaces the phrase in the buffer and the cover is rebuilt to its length. If it does not, nothing happens: no message, no change. There is no recovery for a forgotten phrase. The only sign that the vault is open is the header text (the word count, "Last edited just now" or "Page 1 of 1") drawn in ink instead of grey.

Two tabs of the page in the same browser share one copy: each tab saves on its own schedule and the last save wins. Deleting the copy or changing the phrase in one tab locks the other tabs, which drop any save still on its way instead of writing the old copy back. To stop keeping a copy, open the intro with `?`, untick the box and press Start: the encrypted copy is deleted from the device, whether or not it can still be read. Entering a phrase while the copy is locked opens it instead of replacing it, with anything typed before the intro opened added after the saved text; a phrase that does not open the copy is refused and nothing is overwritten. Entering a new phrase while the vault is open re-encrypts the copy under the new phrase. Esc on the intro applies your choices exactly like Start.

### Saving into a folder

In browsers with the File System Access API (Chrome, Edge and other Chromium browsers, and Brave once its setting is on) the intro screen offers "Choose a folder on this computer". The page keeps the folder handle in IndexedDB and asks the browser for write permission when it needs it. With a folder chosen, Save writes your real text into a new file named by the moment of the click, `YYYY-MM-DD HH-MM-SS.txt` (or `.md`, or `.docx` for a Word document, as picked on the intro screen; a counter goes before the extension if that name is already taken), and shows the name in a toast; nothing is encrypted and no password is asked. The text written is the text on the page when you pressed Save, even if you press Esc while the browser asks for permission. Choosing or forgetting a folder in one tab reaches your other open tabs. Anyone who can open that folder can read those files, and the computer treats them like any document: on a Mac, Spotlight indexes their contents, Quick Look previews them, Time Machine backs them up, and a Desktop or Documents folder synced by iCloud Drive uploads them to Apple. Pick a folder outside Desktop and Documents if that matters to you. In other browsers the button is hidden and Save downloads instead: an encrypted `.sight` file by default, or, if you pick one on the intro screen, a plain `.txt`, `.md` or `.docx` file named by the moment with no password. Both choices are kept in `localStorage`; the download choice works in every browser.

A `.docx` from Save is a minimal Word document that the page writes itself: one paragraph per line of your text, a Word tab for each tab, and no metadata (no author, no dates, no application name; every part of the archive is dated 1 January 1980). LibreOffice gives the text back unchanged apart from one final line break it adds and a byte-order mark it writes; macOS's `textutil` (the text system TextEdit uses) likewise, except that it drops a U+FEFF or a U+FFFC in the text itself, which python-docx returns exactly; Microsoft Word and Pages have not been tried yet. A carriage return in the text ends a paragraph like a line feed. The document the page writes from `tests/fixtures/sample.txt` is kept as `tests/fixtures/sample.docx`; the test suite checks the page's bytes against it, and the Mac app's writer is held to the same two files on its own branch (the App Store candidate). A `.md` file is your text exactly as typed.

### Save file format

Save encrypts the hidden buffer with AES-256-GCM. The key is derived from your password with PBKDF2 (SHA-256, 310,000 iterations, a random 16-byte salt) and the cipher uses a random 12-byte IV, all through the browser's WebCrypto API. The downloaded `.sight` file is JSON:

```json
{
  "format": "plain-sight",
  "version": 1,
  "cipher": "AES-256-GCM",
  "kdf": "PBKDF2-SHA-256",
  "iterations": 310000,
  "salt": "<base64, 16 bytes>",
  "iv": "<base64, 12 bytes>",
  "data": "<base64, ciphertext plus the 16-byte authentication tag>"
}
```

Open checks the shape of the file, refuses a format, version, cipher or kdf field that does not match the above (`"cover-story"` from the project's earlier name is also accepted), refuses an iteration count below 1,000 or above 2,000,000 (so a crafted file cannot hang the tab), derives the key and decrypts. A wrong password or a damaged file fails with the toast "Wrong password or damaged file" and nothing else changes. Those are the parameters; judge them for yourself. There is no password recovery.

## Threat model

What it helps with:

- A casual onlooker who can see your screen sees a document being written, not your text. The tab title, the header and the typing rhythm all fit the cover, and the unlock phrase shows as cover text while you type it.
- Walking away from the machine with the tab in the background: the page clears itself after 10 minutes hidden, including a phrase or password typed but not submitted. (If the tab stays in the foreground, nothing clears on its own. Press Esc.)
- Someone who finds a saved `.sight` file, or the vault copy in the browser's storage, without the password or phrase gets the ciphertext and a rough idea of its length, nothing else.
- Network observers: nothing is sent anywhere, and the page's Content Security Policy makes the browser enforce that.

What it does not protect against:

- Onlookers reading your fingers or lips, or a camera pointed at the keyboard.
- Anyone who can see the screen while you are peeking, or who looks at your clipboard after you copy.
- A compromised machine. Malware, a hardware or software keylogger, or screen recording captures keystrokes and pixels before the page ever sees them.
- Browser extensions. An extension with access to the page can read its DOM and JavaScript state, including the hidden buffer.
- Corporate monitoring: endpoint agents, managed browsers, data loss prevention tools and screen recording all sit outside the page.
- A forgotten password or phrase. Neither the file nor the vault copy can be opened without it.
- A weak phrase. Anyone who can read the browser's storage on your device can try phrases offline; the slow key derivation helps, a long phrase helps more.
- The browser's own memory. While the page is open, the plain text is in the browser's memory, and a crash dump or swap file could hold it.
- Shared computers. The vault copy stays on the device after Esc; on a machine other people use, leave the vault off or delete the copy before you leave.
- Plain files. Saving into a folder, or choosing a plain `.txt`, `.md` or `.docx` download, writes your words unencrypted to disk, where any program, backup or person with access to that folder can read them; on a Mac, Spotlight indexes the contents, Quick Look previews the files, and a synced Desktop or Documents folder uploads them to iCloud Drive, and a browser set to open downloads may display them at once. Use the encrypted download or the vault when that matters.

Corporate IT may treat a page like this as an exfiltration or monitoring-evasion tool. Using it on a managed machine may break policy regardless of what you type. It exists to demonstrate a client-side technique and an honest threat model, not to defeat an employer's monitoring.

## Known limitations

- No mobile support. Virtual keyboards do not reliably fire `keydown` events, so typing on a phone or tablet does not work. The layout does not overflow at phone widths, but the page is a desktop tool.
- Only key presses are recorded. Text that arrives another way, such as a paste, drag and drop, dictation or the composed text of an input method editor, is neither recorded nor shown.
- Characters that need Alt, Option or AltGr on your keyboard layout (for example @ or { on many non-US layouts, or accented letters typed with Option on a Mac) are passed to the browser and not recorded, because every Alt chord is left alone.
- The hidden text is append-only. You can peek, copy and backspace, but not move the cursor back and edit.
- The page has to be served over http (see "Run locally"). Opening `index.html` directly shows a notice instead of a cover.
- Peek, copy and unlock are keyboard chords, so they do not work from a touch screen.
- Saving into a folder needs the File System Access API, which Chromium browsers offer (Brave behind a setting) and Safari and Firefox do not; those two get a download instead: the encrypted `.sight` by default, or `.txt`, `.md` or `.docx` by choice. The folder path was checked here with a simulated folder in the test suite; the plain download was checked in headless WebKit; real-browser runs on this version are listed in the browser table.
- With the vault on, the page saves 1.5 seconds after the last keystroke and again when the tab is hidden, on Esc and on the way out of the page. Closing or reloading the tab within about a second of typing can still lose those last keystrokes from the copy, because the browser may not wait for the encryption to finish.
- Tested headless in WebKit (Safari's engine) on version 1.4.0 on 21 and 22 October 2026: no console errors, all three covers, the chords, the vault, save and open, and no horizontal overflow at 390px. Current Chrome, Edge and Firefox use the same standard APIs (WebCrypto, ES modules, the Clipboard API with a fallback) and are expected to work, but they have not been checked on this version.

## Being safest

- The Mac app (the `desktop` branch) will be the better choice on shared machines and untrusted networks once it is cleared for others: its gate saw no network use, and no browser extension can reach it. Until then, use the page in a browser profile with no extensions.
- Use the encrypted save or the vault. A plain `.txt` is readable by anyone with the folder, and macOS indexes it for Spotlight and may sync it to iCloud.
- Press Esc when you step away. The peek chord is public, so anyone at your keyboard can use it.
- On a shared network, open the page from an https link or bookmark, never click through a certificate warning, and clear your clipboard after a copy.
- Use a browser profile without extensions. An extension with page access can read anything on the page.

## Planned hardening

Logged on 21 October 2026, in this order: an App Sandbox with no network permission for the Mac app, so macOS itself refuses every connection; Secure Keyboard Entry and a capture-proof window while the real text is on screen in the app; a clipboard that clears itself after a copy; an idle lock that wipes the screen and locks the vault, in the app also when the Mac locks; a higher PBKDF2 round count once the vault carries the count with its key; the security headers served by the host; and encrypted, plainly named files for folder saves. Where each stands on this branch: the App Sandbox exists, signed into the Mac app, and was launched as probe builds under test identifiers on 26 October 2026: with the candidate's three entitlements the page gave no answer in 31 seconds, and with com.apple.security.network.client added it answered in 2.5 seconds and a picture of it was taken (both probe builds also carried a temporary exception for the probe's own folder, so the one difference between them was the network entitlement), so the sandbox cannot be what refuses network use for this app; the build as it stands, with the three, would open no page in the sandbox, and whether to add the entitlement is Pranav's decision (the section below says what that means). The security headers exist, served by the host since 1.3.10 (`vercel.json`, which `npm test` checks against the page). Secure Keyboard Entry and the capture-proof window do not exist yet. The self-clearing clipboard does not exist yet. The idle lock does not exist yet. The higher PBKDF2 round count does not exist yet. The encrypted, plainly named folder saves do not exist yet. Each will appear in the changelog when it does.

## Desktop app (Mac)

The same page also runs as a Mac app, built from the `desktop/` folder: a small native shell ([Tauri](https://tauri.app) 2) around the page and its covers, shown in macOS's own web view (WebKit, the engine Safari uses). It is the same `index.html` with one marked addition for the app: a branch that uses the app when the app is there (search for `native`) and the app's wording in `data-app` attributes. In a browser neither does anything. The app is about 3 MB, is built for Apple silicon Macs and declares macOS 12 as its minimum (Tauri's rule for an Apple silicon only App Store build; it was tested on macOS 26 only), and its changes are listed in `desktop/CHANGELOG.md`.

What the app adds to the page:

- **Save into a folder on every Mac.** "Choose a folder on this computer" opens macOS's own folder panel. From then on Save writes your real text into that folder as a file named by the moment you pressed it, `YYYY-MM-DD HH-MM-SS.txt`, or `.md`, or a Word `.docx`, as picked under "Files in the folder are"; a name that is already taken gets ` (2)`, ` (3)` and so on, and an existing file is never overwritten. The app makes the Word document itself from your text, byte for byte the one the web page makes, so the page never hands the app a file to write. The app remembers the folder across a quit as a security-scoped bookmark (`folder.bookmark` in its own data folder), which is how an app in the macOS App Sandbox gets back into a folder; the page itself only ever learns the folder's name. A folder kept by an earlier build as a plain path is not used: the page asks for the folder again. "Stop using the folder" forgets it. If the app cannot keep or forget a folder, the page says so and nothing changes.
- **Save without a folder** shows macOS's own save panel, starting in your Downloads folder with the name the web page would use (the encrypted `.sight` file, or a plain `.txt`, `.md` or `.docx` file named by the moment, as picked on the intro screen); the file is written where you put it, under that format's extension (the panel should give a name typed without one that extension; if it does not, the app refuses the name and the page says "Could not save"; not yet seen on screen; the app refuses to write one format's bytes under another's name), replacing an existing file only after the panel has asked you and in one step, so a write that fails halfway (a full disk, say) leaves the existing file as it was; a folder or a link to another file at the chosen name is refused, as is a file in a folder you may not change; and the page says "Saved" only once the app has written it ("Could not save" otherwise; Cancel says nothing). The first time the app writes into a folder macOS guards, it may ask whether Plain Sight may use that folder; if the answer is no, Save says "Could not save" or "Could not write to the folder". (The test build, never the app you run, can be pointed at a folder through `PLAIN_SIGHT_E2E_DOWNLOADS` and given the panel's answer through `PLAIN_SIGHT_E2E_SAVE_AS`, so the end-to-end tests never touch the real Downloads folder.)
- **Quitting and closing work like Esc, after a question.** If the page holds text that no open vault keeps and that changed since the last Save or Open, closing the window (its close button or Cmd+W), quitting (Cmd+Q or the Plain Sight menu) and a quit from the Dock or a logout first ask "Quit without saving?" in a sheet on the window: Cancel, the default button, keeps the app open with everything as it was (and stops a logout or shutdown, as any document app with unsaved changes does); Quit goes on. With a vault open, with nothing on the page, or right after a successful Save or Open with nothing typed since, there is no question (a keystroke or Backspace after the Save brings it back; so does typing back to the saved words, since the page counts its edits since the last Save or Open and keeps no copy of the saved text to compare: a needless question then, the safe direction). The quit then erases the screen and the hidden text. An open device vault is saved and locked first, and then the app gives WebKit about a second to write that last save before it ends (WebKit writes a save about half a second after it gets it; the app waits for that, it does not read the disk back), so a quit takes about a second. If the page never answers the question, the quit goes on after 1.5 seconds, and if it then never says it is done, the app's own timer ends it after 4 more seconds, so about 5.5 seconds in all. Esc stays the deliberate erase, with no question.
- **A document window.** The title bar names the cover on screen, the menu bar has only standard items, a right click on the page shows no menu (the text fields keep theirs), and the intro's wording speaks of the app instead of a browser. File > Open... (Cmd+O) and File > Save... (Cmd+S) press the page's own Open and Save buttons, and Help > Plain Sight Help opens the intro (the ? button); all three do nothing while the intro or the password dialog is open. The window is marked not restorable, so macOS should keep no picture of it under Saved Application State: in the end-to-end run of 26 October the window reported itself not restorable and a forced end while peeking left no window state there; the same check after a normal quit has not run to a result yet.
- **The device vault** works as on the web; in the app its encrypted copy is kept with the app's own web data, which in the sandbox lives in the app's container (`~/Library/Containers/com.pranavongole.plainsight`); at the first sandboxed launch macOS brings an earlier copy there; in a probe build on 26 October 2026 (macOS 26) it moved the data, although Apple's article says it copies it, and folders under the probe's identifier stayed outside the container, `~/Library/WebKit/<id>` (empty) and `~/Library/Caches/<id>` (sbprobe2-run-1, `leftovers`); keep a copy of the data before the move (D-54).

How it is kept honest: the app serves the page's own Content Security Policy a second time as a header, so a blocked request is refused by two copies of the same policy. It shows nothing but its own page (navigation away and new windows are refused). The page can call exactly six app commands (five for the folder and Save, one to say it is ready to quit), and into the chosen folder the app accepts only the file names and the three plain formats Save makes, while through the save panel the person names the file and the app writes under that name; it is handed text only, never the bytes of a file. The app asks the page one thing in return, before a quit: whether it holds text a quit would lose. None of the crates the app is built from is a network library. A network watch (the app's open sockets read every 0.6 seconds or so, and macOS's `nettop` on every interface) saw no socket and no traffic from the app or its web view in the 1.0.0 gate on 21 October 2026, on aa190a3, unsandboxed, around a full run of the end-to-end tests (nine launches of a test build: saves, folder writes, the vault, every way to quit, and attempts to load a web address) and around the release app's own tests (four launches); the same watch does report a connection made on purpose. That is an observation of those runs, not something macOS enforces; see the limits below. The one watched run of a sandboxed build, a test copy of this branch on 26 October with three entitlements and the screen locked (release-run-1), saw the app's four launches and recorded no networking process; the watch then looked only for the unsandboxed web data paths, which a sandboxed app's data never matches, so it could not have recorded one (whether one was running in those launches was not shown; a probe copy with those three entitlements and a temporary exception for its own folder gave no answer from its page in 31 seconds); it now matches a sandboxed app's container too (round 7) and has not watched a sandboxed launch since.

What changes in the threat model inside the app:

- No browser extension can reach the page.
- macOS features that a person starts by hand (Services, Look Up, Dictation, AutoFill, and Writing Tools in the Edit menu) can still pass selected text to other apps or to Apple, as in any app. The app turns Writing Tools off for the page, and WebKit reports the setting as off; whether the Edit menu's Writing Tools item then does nothing with selected page text has not been tried.
- The vault copy is written 1.5 seconds after you stop typing and is on disk a second or so later. If you type without a pause of 1.5 seconds, nothing new is saved until you pause, so a Force Quit, a crash or a power loss in that stretch loses what you typed since the last pause. Esc, closing the window and quitting save first; closing and quitting also wait for WebKit to write the save, while after Esc WebKit writes it about half a second later.
- If the page's web process crashes, the app reloads the page: the hidden text is gone and an open vault is locked again, with its copy as last saved. Nothing tells you this happened.
- The app is signed with the macOS App Sandbox and three entitlements (files you choose in a panel, app-scoped bookmarks, and the sandbox itself), none for the network and none for the Downloads folder, since Save without a folder goes through the panel. In the probe builds of 26 October the page gave no answer in 31 seconds in the sandbox without the network entitlement and answered with it, and the candidate still carries three; the build as it stands would open no page (ledger 26 October, 19:51), and whether to add the entitlement is Pranav's decision. Known gap: if markup could ever be injected into the page, a link click or a preconnect hint could still open a TCP connection (QA saw the connection open; no request was sent on it). The shipped page has no such markup, and QA found no way to inject any.

To build and run it you need Node, Rust through rustup and the Xcode command line tools (it was built with Node 24.18 and Rust 1.99.1):

```
npm --prefix desktop ci
npm run app:dev       # opens the app; the first build takes a few minutes
npm run app:build     # desktop/src-tauri/target/release/bundle/macos/Plain Sight.app
```

A copy built on your own Mac opens with a double-click. The app is signed ad hoc, not with an Apple Developer ID (`spctl`, the check macOS applies to an app from elsewhere, rejects it), so a copy that arrives by download, AirDrop or email is refused the first time; `desktop/SIGNING.md` explains the way past that and the steps to sign and notarize the app. One caution for a Mac that already runs the unsandboxed app with notes in it: the bundle this branch builds is sandboxed under the app's real bundle identifier, and the first time such a bundle opens, macOS creates the app's container and brings the app's data into it, once (ledger D-39). So until that move is meant, do not open that bundle, neither by a double-click nor through `test:release` or `test:app`: both suites refuse a bundle sandboxed under the real identifier (in its `Info.plist` or its signature, in any case) before they move any data aside, and `npm --prefix desktop run app:testcopy` makes the copy they run on instead (`desktop/tests/testcopy.mjs`): the same bundle under a test identifier and the name "Plain Sight test copy", signed ad hoc again with the same entitlements, with its migration manifest left out so that it never copies the real vault into its own container; the script prints the copy's path for `PLAIN_SIGHT_APP=<that path>`. `PLAIN_SIGHT_ALLOW_REAL_ID=1` lifts the refusal, for the deliberate run after the move. Delete the real-identifier bundle once `test:bundle` has checked it.

Tests: `npm test` (after `npm ci`; its test library runs on Node 22.22.2 or later, 24.15 or later, or 26 and up) runs the web suite, the app's jsdom, adapter, config and copy tests, the test harness's own safety checks (the backup and restore of the app's data, the order of its signal handlers, how a run ends when macOS refuses to move or remove a folder, its refusal of a locked screen and of windows listed only off-screen, and the fresh copy a test gets for a first launch of a sandboxed copy) against a fake home inside a temporary folder, with no app and no driver, and the launch guard's tests on fake bundles (nothing signed or opened). `npm --prefix desktop run test:rust` runs the app's Rust tests and `npm --prefix desktop run lint:rust` its formatting and lint checks; both copy the page into `desktop/frontend` first, which `cargo test` and `cargo clippy` need (run by hand in `desktop/src-tauri` before that copy exists, they stop with a message naming `npm run copy`). `npm --prefix desktop run test:bundle` checks the built app itself. `npm --prefix desktop run test:e2e` (after `npm --prefix desktop run build:e2e`) runs a test build and drives it from inside the page; `npm --prefix desktop run test:release` opens the release app through LaunchServices and ends it each way it can without key presses; `npm --prefix desktop run test:app` drives the release app with real key presses through macOS (until the move above, both of these run on the test-identifier copy, `PLAIN_SIGHT_APP=<the copy>`, never on the built bundle itself). These three need the Accessibility permission for the program that runs them and an unlocked, idle Mac with the display on (the end-to-end and release suites listed no on-screen window with the screen locked on 26 October, so run them unlocked): they do not start while the screen is locked (exit code 4), stop as not run when a launch's window is listed only off-screen (exit code 3), start only when the Mac has been left alone, stop at the first touch of the keyboard or mouse, take turns through a lock file, and put the app's data and the clipboard back as they were. A Ctrl+C or a kill (the harness handles SIGINT, SIGTERM, SIGHUP and SIGQUIT, which `Ctrl+\` sends) ends a run with exit code 130 only once everything is back: one that comes while the run is putting things back, or a second one, is reported and waits for that, and a cleanup that never ends holds back every signal until it ends. A SIGKILL cannot be handled: it ends the run at once with the data still aside, and the next run then refuses to start and names what to put back. From the first signal, or from the moment a run begins putting things back, no test launches the app again (the launch is refused and that test stops as not run), and the suite's end stops the app that is current when its wait ends (the release and real-key suites stop every copy running from a bundle the run opened, recorded or not), so no app the run started outlives it, unless its process would show only after the run had ended (more than 15 seconds after its launch, QA-01's T4); before round 9 a test that went on after a Ctrl+C could launch the app again once everything was back, and a launch of this branch's build removes the 1.0.0 app's folder choice (DM-249). Once it has put the app's data back, a run checks it: it lists each folder it moved aside as it moves it and again after the restore, at once and 3 seconds later (every file's path, size and modification time, never its contents), and checks that no app it launched is still running; any difference is named by its path or pid and ends the run with exit code 6, after a Ctrl+C as well, and a clean check says so in one line before the summary. The harness notes "stopping pid <n>" in its run.log as it begins to end an app, so a deliberate Ctrl+C can be sent while a test waits there. A run that cannot put the app's own data back ends with exit code 6 and says where it waits. Test data that macOS will not let a run remove, such as the container a test copy's launch made, is left where it is and named, and the run then ends with exit code 8 (test data left behind; your own data is back) when no test failed and nothing stopped it; every run that ends by its own count (not by a signal) lists the test containers on the Mac by name, without opening them, for removal by hand. A test copy runs once: a run on a copy whose container is still there does not start, so each run needs a fresh copy from `app:testcopy`. On a sandboxed copy the real-key suite's three tests that start again from a first launch (the folder picker, the quit sheet and the vault) never clear the copy's data mid-run, since macOS refuses to let a run remove a copy's container (EPERM, as at the end of release-run-1): each makes a fresh copy of the bundle under test with the copy script's own function, under a new test identifier, into the run's evidence folder, and launches that one, so a run on a copy can leave four test containers, all named at its end as test data left behind (exit code 8). An unsandboxed bundle's folders are still cleared as before. A person may instead allow the program running the suites to access other apps' data once; the clears of those containers at the end of a run should then work as well (not yet tried). The three suites write into no personal folder: the test build saves its downloads into a folder under the run's evidence directory, and the real-key save and folder tests type a folder of their own there into the panel's Go-to box and press the panel's default button only once the panel shows that folder (otherwise they cancel the panel and fail, rather than save into the panel's start folder).

## Run locally

```
git clone https://github.com/PranavOngole/plain-sight.git
cd plain-sight
npx serve -l tcp://127.0.0.1:3000 .
```

Then open http://localhost:3000. The `-l` option keeps the server on this computer only; `serve` listens on every network address by default, which would expose anything else in the folder. Any static file server works; the page needs http only so the browser will import the cover modules. Use localhost or https: on any other plain http address the browser gives the page no encryption, so the vault and encrypted files cannot work there, and the intro says so.

To run the tests:

```
npm install
npm test
```

The suite (`tests/smoke.mjs`) loads the real `index.html` in jsdom and drives it through keyboard events, the dialogs, the download path and the console object: cover rendering, the hidden buffer, the peek chord, copy, Backspace, Esc, the 10-minute wipe, the three covers, bullets, headings, references, save and open with right and wrong passwords, and the device vault with right and wrong phrases. It exits non-zero on any failure. jsdom does not run module scripts, so the suite imports the cover files itself and hands them to the page the same way the module loader does.

## Deployment

The site is served with security headers from `vercel.json`: a script policy that allows only the page's own two inline scripts by hash, no framing, no content sniffing, no referrer and no browser features. `node tools/vercel-headers.mjs` regenerates the file from `index.html`, and `npm test` fails when the two disagree, so a changed page cannot ship with a stale policy.

The site is deployed with the Vercel CLI (`vercel --prod`) as plain static files with no framework and no build step. `.vercelignore` is an allowlist: everything is excluded except `index.html` and `covers/`, so nothing else in the working folder can reach the deployment. Until 20 October 2026 it was a list of exclusions and the deployment carried local tool files; see the changelog for 1.3.1.
